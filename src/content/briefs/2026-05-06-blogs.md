### Cloudflare’s serve-stale cushion during the .de DNSSEC outage

On May 5, DENIC, the registry for Germany’s .de top-level domain, published broken DNSSEC signatures, making millions of domains unvalidatable and unreachable for resolvers that enforce validation. Cloudflare’s 1.1.1.1 resolver saw a surge of SERVFAIL responses and used its “serve stale” feature to keep expired but known-good records in circulation while upstream signatures were broken. Resolution was fully restored only after Cloudflare temporarily disabled DNSSEC validation for the .de zone.

The incident is a sharp reminder that DNSSEC’s security mechanism can become its own single point of failure. Serve stale cushioned the impact but was a temporary patch, not a fix. The bigger structural problem is that a TLD operator can break its zone without a graceful rollback, and the recovery path depends on resolver operators choosing to override a security policy they normally enforce.

**Key conclusions**

- A single misconfiguration at DENIC rendered .de domains unreachable for validating resolvers worldwide.
- Cloudflare’s serve-stale feature mitigated the outage by temporarily serving cached records past their TTL.
- Resolution was fully restored only after Cloudflare disabled DNSSEC validation for .de, trading security for availability.
- The event exposes the fragility of DNSSEC when TLD operators lack automated recovery mechanisms.

([Cloudflare Blog](https://blog.cloudflare.com/de-tld-outage-dnssec/))

### Using dominatory analysis to validate agentic coding behavior

GitHub researchers argue that traditional, deterministic tests break down for AI coding agents whose tasks have many valid solutions. They propose a “Trust Layer” that uses dominatory analysis — checking whether the agent’s proposed change is strictly non-regressive against a set of user-defined quality rules, rather than requiring an exact correct output. The rules compare metrics such as linting, test pass rates, and static analysis results between the previous code state and the agent’s suggestion.

The post is a research preview, not a shipped feature. The dominatory analysis concept elegantly sidesteps the brittleness of scripted tests and the opacity of LLM-as-judge evaluations, but it shifts the burden entirely onto defining rule sets that truly capture what “better” means. Without those rule definitions being sound, fast, and complete, the Trust Layer could become a false-green-lights machine.

**Key conclusions**

- GitHub proposes dominatory analysis to check that agentic code changes are non-regressive without requiring a ground-truth output.
- The Trust Layer compares proposed solutions to the previous state across configurable quality metrics.
- The approach is still experimental; no production timeline or user-facing tool has been announced.
- The post sidesteps the challenge of defining comprehensive rule sets that avoid both false rejects and missed regressions.

([GitHub Blog](https://github.blog/ai-and-ml/generative-ai/validating-agentic-behavior-when-correct-isnt-deterministic/))

### Vercel open-sources deepsec to find vulnerabilities with coding agents

Vercel released deepsec, an open-source security harness that uses coding agents — powered by a user’s Claude or Codex subscription — to scan large codebases for vulnerabilities. The tool runs entirely on local infrastructure, avoiding the need to upload source code to a cloud service, and can optionally fan out parallel execution to Vercel Sandboxes to reduce scan time. Vercel says it routinely scales scans of its own repos to hundreds of sandboxes.

Running agent-driven security scanning locally is the right trust model, but the accuracy story is still blank. Deepsec’s real false-positive rate and coverage against known vulnerability classes will only emerge when third-party teams stress-test it on messy, real-world repos. The immediate practical question is how long a typical scan takes and whether the output is actually actionable, not just longer than a static analyzer’s.

**Key conclusions**

- deepsec uses AI coding agents to scan codebases for vulnerabilities, running on the user’s own machine.
- Parallel execution via Vercel Sandboxes can accelerate scans of large repos, but incurs cost and sandbox dependency.
- The tool is open-source and works with existing Claude or Codex subscriptions, removing upfront licensing barriers.
- Real-world effectiveness is unverified — false positives, scan duration, and coverage against known vulnerability classes remain open questions.

([Vercel Blog](https://vercel.com/blog/introducing-deepsec-find-and-fix-vulnerabilities-in-your-code-base))

### General Intelligence runs 4,000 preview branches and automates 90% of SRE on Vercel

General Intelligence, an eight-person startup building the agent-launching platform Cofounder, reports that its five engineers average 70 commits and 10 pull requests per day while maintaining over 4,000 preview branches and about 100 parallel live app versions. The team has automated 90% of its SRE work through Vercel’s infrastructure and its own agent tooling, and it provisions a fully managed Vercel account for each Cofounder customer automatically.

Those productivity numbers are extreme, and they come from a single vendor case study. It’s plausible that an agent-first toolchain plus Vercel’s platform compresses the build-deploy-feedback loop dramatically for a product that is itself an agent platform. But we can’t disentangle how much of this velocity is due to infrastructure versus a founder-heavy, all-senior crew building a greenfield prototype. The figure that would make this real is replication by an unaffiliated team.

**Key conclusions**

- General Intelligence reports 70 commits/10 PRs per engineer per day and near-total SRE automation.
- 4,000+ preview branches and 100 parallel app versions indicate extreme CI/CD parallelism on Vercel.
- The case study is a vendor narrative; productivity gains are not independently verified or easily generalizable.
- High automation may be tightly coupled to the team’s deep expertise with both Vercel and their own agent platform.

([Vercel Blog](https://vercel.com/blog/how-general-intelligence-used-agents-to-build-an-agent-platform-on-vercel))
